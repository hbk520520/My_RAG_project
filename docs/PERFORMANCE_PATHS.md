# 第一阶段性能路径：批量编码与快照索引复用

当前状态：实现完成，两个配置开关默认关闭。本轮按要求不运行测试和基准，尚未证明数值等价、检索结果一致或性能收益；不能把静态检查视为运行验收。没有新增依赖，也没有引入 CUDA／Triton 算子。

## 开关与原实现

`config.yaml` 的 `performance` 配置：

| 配置 | 默认值 | 用途 |
|---|---|---|
| `batch_encoding` | `false` | 为默认编码器启用批量路径 |
| `encoding_batch_size` | `32` | 每次交给编码器的文本数，正整数；尚未调优 |
| `snapshot_index_cache` | `false` | 默认 Agent 引擎使用快照索引缓存 |
| `snapshot_cache_entries` | `2` | 每个服务实例最多保留的序列化索引数 |
| `snapshot_cache_max_bytes` | `268435456` | 保留的序列化 CPU 索引总字节上限 |

关闭开关仍走原路径。`LegalDenseGraphBuilder.encode_text` 未改动；语料原实现保留于 `_vectorize_reference`；任务原实现保留于 `AgentService._reference_pinned_engine`。显式注入的单条编码函数继续逐条调用；显式注入自定义 `engine_factory` 的服务不启用缓存路径。缓存配置在创建服务实例时读取，调整后需重建服务实例。

`encode_texts` 和 `vectorize_batch` 也允许调用方显式使用，无需开启全局开关。它们要求批量编码契约，不把单条编码函数自动转换成批量函数。

## 批量编码

`dataset/encoding.py` 负责按字符长度分组、限制每批文本数、归一化 dense 向量并恢复原始行顺序，同时保留逐条 sparse 权重。它不改变分词器、截断策略和模型；字符长度只是分组依据，不是 token 预算。校验输入类型、输出维度、有限值和 sparse 行数，错误直接抛出，不静默退回逐条路径。零向量保持零值；空输入不加载编码模型。

接入三处：语料 `vectorize`、未提供预计算向量的初始建图、PageIndex 文档原文页入库。预计算向量路径保持原样；PDF 页仍按物理页顺序加入图，事务范围不变，只有当前一批页的编码结果驻留。层次摘要存在父子依赖，继续使用原来的生成和编码流程。

语料和初始建图仍需保存完整输出矩阵；批量大小只限制一次编码调用，不限制总语料内存、长文本 token 数或模型内部临时内存。并发编码仍受既有模型资源管理约束，本组件不新增 GPU 调度或 OOM 重试。

## 快照索引缓存

`dataset/index_cache.py` 仅保留本进程构建的 FAISS 索引序列化字节。键由项目命名空间和完整规范化快照的 SHA-256 构成，包含向量、节点、图配置与嵌入空间信息。快照改变即产生不同键，旧条目按 LRU 淘汰。超出字节上限的索引可以供当前任务使用，但不保留。

冷启动在锁内构建并序列化，避免并发启动重复构建同一快照；不同快照的冷构建也会串行。缓存命中时反序列化出任务独享索引；图和元数据每次独立恢复，不共享可变引擎。保留上限只约束缓存字节，不包含活跃任务索引、图、哈希输入和构建／反序列化临时内存。它不使用显存，不写索引文件，也不接收外部序列化索引。

`AgentService._cached_pinned_engine` 先读取任务固定快照。恢复已有任务时不再先恢复当前项目语料；首次任务读取当前项目快照后固定版本。原有嵌入空间、图配置、运行配置和 Prompt 检查保留。任务快照格式、运行库结构和历史配置哈希字段不变；性能开关不加入历史哈希字段。不要在同一运行中切换编码策略来解释数值差异。

缓存仅属于一个 `AgentService` 实例；不同服务实例、进程和重启之间不共享。每个任务仍保存完整快照，且仍支付 JSON 读取、完整快照哈希、图恢复和私有索引内存成本。这里没有实现快照去重存储、跨进程共享或零拷贝。

## 计时口径与后续验收

新增 INFO 日志不记录原文、向量或密钥：

| 日志 | 计时范围 |
|---|---|
| `corpus_encoding` | `vectorize` 路径，包括该路径触发的模型首次加载 |
| `batch_encoding` | 分组后的编码循环、向量校验与归一化；不包括输入准备和长度排序 |
| `knowledge_view` | 任务知识视图完整构造，包含固定快照读取和保存 |
| `snapshot_index_cache` | 缓存查找及锁等待；未命中含构建和序列化，命中含反序列化 |

这些是同步调用的墙钟时间，不是 CUDA Event 算子计时。异常退出时外层 `corpus_encoding`、`knowledge_view` 也会记录耗时，日志本身不是成功标记。没有配置 INFO 日志输出时不会自动生成测量文件。

后续获准运行验证时，先用同一模型版本、语料、精度、设备与并发配置对照原实现：

1. 编码：覆盖空输入、重复文本、末尾不足一批、零向量、异常形状／非有限值；检查行顺序、sparse 一一对应，并预先规定 dense 误差容限。再核对检索排序和临近建边／去重阈值的行为；不能只比较矩阵形状。
2. 缓存：检查同快照构建次数、项目／快照隔离、LRU 数量和字节淘汰、超大条目不保留、并发启动与构建失败传播。修改一个任务的索引或元数据不得改变另一个任务。
3. 运行恢复：覆盖新任务、已有固定快照、当前语料已更新、取消／恢复、配置与嵌入空间不匹配；确认恢复遵循原固定快照。
4. 性能：分别报告模型冷／热启动、缓存冷／热路径和完整任务启动的耗时分布、吞吐、CPU 内存与设备峰值内存。计入哈希、序列化、反序列化和锁等待成本；有效性不通过或总体无收益时继续使用关闭开关的原路径。
