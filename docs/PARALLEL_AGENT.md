# 工具策略、并行与共享资源

当前实现在单机/受信小团队范围内工作，复用 LangGraph、SQLite、线程池与操作系统文件锁。
没有新增依赖，没有修改数据库表结构，没有实现 Triton/CUDA 算子或声明实际加速比例。

## 任务与模型职责

Planner 输出依赖 DAG，任务仍保留 task_id、task_desc、deps、engine、rationale；新增：

- evidence.navigation：auto / vector / agent。auto 遵循部署导航配置。
- evidence.causal：auto / off / verify / temporal。
- evidence.analysis：facts / reasoning。
- revision：任务计划版本，重规划后递增。

原有引擎 GRAPH_TRAVERSAL、GLOBAL_DENSE_WORMHOLE 继续兼容。目录导航与因果分析可以组合，
不把所有工具塞进互斥的引擎枚举。旧任务缺少 evidence 时使用 auto/facts 默认值。

新 Planner 提示要求普通法规问答关闭因果分析；需要结论推导时显式选择 reasoning。
兼容任务的 causal=auto 按明确截止日/目标或因果问题词决定是否调用 CHAIN，是启发式策略，
没有声称该分类器经过质量评测。显式 verify 只验证文本因果支持；temporal 要求截止日和目标实体。
verify 在提供截止日时仍过滤不合格证据，但不计算 CTVF。目标无法锚定时保留原有明确状态。

Extractor 与因果验证使用不同角色调用；Grader 提取事实、判断充分性，评分理由独立保存，
不再当成业务推理。analysis=reasoning 且证据充分时才调用 Reasoner；Generator 汇总与生成引用。
Replanner 仅修改失败分支；完整性硬规则在合并后的观察上检查，包括最后一个任务完成时。
规则生成的步骤暂按规则顺序串行，模型 DAG 中的独立分支可以并行。

llm.role_models 可按角色覆盖 API 模型，未配置时共用原 judge_model。
vllm.role_adapters 显式映射角色到已有适配器名；不在运行时切换全局可变角色。
同名适配器复用稳定 ID，不同适配器使用不同 ID；指定不存在的适配器明确失败。
配置映射不代表权重已经存在、训练完成或具备新动作选择能力；真实权重与质量仍需独立验收。
因果校准标识随提取/验证角色模型配置变化，并写入审计；默认 API 角色配置继续兼容旧标识。
模型配置不匹配的校准文件明确拒绝使用，不能把旧模型的校准效果移植为新模型的效果。

## 图和证据

语义边与目录关系继续复用现有知识图、原文节点和文档版本。每次运行固定一个知识快照，
并行分支共享这个只读视图和文档阅读器，不为每条分支复制整份图或加载编码器。
分支检索轨迹独立；事实引用以文档版本、页码、证据 ID 和原文为依据。

普通任务将原文记录保存于 source_evidence，因果任务继续保存于 causal_evidence。
最终引用校验同时读取两者。不使用目录摘要作原文证据，不从相似边推导因果边。
SCM 保留在离线评测模块，未注册成在线工具。

FAISS 自有向量、图节点向量和运行快照仍有 CPU/磁盘重复，这是当前检索与恢复契约的一部分。
本次没有宣称原文物理存储完全去重，也没有迁移到新的不可变版本存储。
截至日过滤在证据交给事实判断/因果提取前执行；目录导航可能已经看过文档目录与摘要，
因此这些工程检查不能证明历史预测的全流程无时间泄漏，需另做历史可用性评测。

## 调度与恢复

Executor 选择依赖已完成的任务，最多启动 scheduler.max_parallel_tasks 条分支。
线程池只接收本轮有界任务；分支返回结果，由唯一协调器按计划顺序合并，不按完成快慢改写事实顺序。
当前是有界批次/屏障式推进，批次结束后再启动下一轮，并非任意粒度的连续调度。

分支拥有独立 RunContext，执行记录包含任务 ID、revision、运行 epoch 与输入摘要。
任务结果先进入现有 effects 台账，然后由 LangGraph 提交协调器检查点。
兄弟分支失败或进程退出时，已经落盘的成功结果可以复用；只有未完成的读取可能重做。
取消/回滚仍通过租约与 epoch 阻止旧分支写入。外部供应商已发生的请求不能撤销。

多个问题按任务依次请求用户补充，答案保存在 task_user_facts；只向对应任务及显式依赖它的任务传递。
用户补充与检索原文始终分离。恢复保留原 deadline 和调用预算，不充值、不重置。

运行库以原 runs 表的有效租约数量限制并发，默认 max_running_runs=2；同一运行仍只有一个有效拥有者。
恢复扫描按提交顺序取有界批次。没有实现严格公平、任务抢占或多机调度。
Kafka 消费线程只校验已持久化任务通知并提交位移，独立执行线程扫描运行库，避免执行期间停止轮询。

## 部署资源

scheduler 配置控制运行、分支、远程模型、本地模型、编码器、沙箱的额度，以及等待队列和模型缓存数量。
额度为部署配置，不绑定任何显卡型号。OS 文件锁跨同机进程限制操作并发，进程退出自动释放。
所有进程必须使用相同资源目录和额度配置；运行时不根据显存空闲快照猜测安全并发数。
资源等待、工具完成记录包含等待/执行时间和任务标识，可作为之后性能基线的采集入口。

编码器按模型、设备、精度、维度、嵌入空间版本共享，缓存有数量上限；注入的自定义编码器保留自己的身份。
编码器拥有者串行调用模型，本次未实现跨任务微批处理。只读图可被多个分支访问。
本地 vLLM 在同一进程复用一个实例并受并发额度约束；改变已加载模型配置要求重启拥有者。

为防止不同进程重复把权重装进显存，默认本地加速器模型由一个执行进程持有 OS 拥有者锁。
该进程可并行推进多个运行；意外的第二个本地模型进程在加载前明确失败。
推荐部署：本地模式由 API 内的执行线程运行；Kafka 模式 API 用 serve --kafka，只提交任务，由 Worker 执行。
直接 CLI 进程若与活跃的 GPU 模型拥有者冲突，应通过该拥有者的 HTTP/Kafka 入口提交。
这不是跨进程共享 Python 模型对象，也不是显存字节级分配器。驻留权重、KV/激活、缓存数量需按部署测量配置；
CPU、不同设备和远程推理服务均可配置，未新增多 GPU 自动放置或分布式推理实现。
